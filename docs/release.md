# Как выпустить релиз

Приложение раздаётся образом DMG мимо App Store, а обновления приходят через
Sparkle. Чтобы человек, который поставил Wai Dictation, получил новую версию,
нужны три вещи: подписанный и нотаризованный образ, подпись обновления и
запись в ленте.

Всё это делает `scripts/release.sh`. Ниже — что подготовить один раз и что
проверять каждый раз.

## Один раз: ключ обновлений

Sparkle не поставит обновление, которое не подписано вашим ключом. Пара
ключей создаётся один раз на все версии и на все приложения.

```bash
BIN=~/Library/Developer/Xcode/DerivedData/WaiDictation-*/SourcePackages/artifacts/sparkle/Sparkle/bin

# Создать пару. Приватный ключ уедет в связку ключей, публичный напечатается.
$BIN/generate_keys

# Выгрузить приватный ключ в файл — он понадобится скрипту релиза.
mkdir -p ~/.wai-dictation
$BIN/generate_keys -x ~/.wai-dictation/sparkle-key
chmod 600 ~/.wai-dictation/sparkle-key
```

Дальше:

- **Публичный ключ** впишите в `apps/macos/project.yml` как `SUPublicEDKey`
  (там для него оставлена закомментированная строка). Он публичный — его
  место в репозитории, приложение проверяет им подпись.
- **Приватный ключ** не коммитьте никогда и не кладите в репозиторий даже
  временно. Держите его в связке ключей и в резервной копии: без него новые
  версии перестанут приезжать тем, кто уже поставил приложение. Второй ключ
  завести нельзя — старые копии приложения о нём не знают.

Инструменты Sparkle (`generate_keys`, `sign_update`) приезжают вместе с
пакетом: Xcode распаковывает их в DerivedData при первой сборке. Отдельно
ставить ничего не нужно. Если путь другой — передайте его переменной
`SPARKLE_BIN`.

## Один раз: подпись приложения и GitHub Pages

- Сертификат **Developer ID Application** в связке ключей.
- Профиль нотаризации: `xcrun notarytool store-credentials`.
- В настройках репозитория: **Settings → Pages → Source: Deploy from a
  branch → `main` / `/docs`**. Оттуда раздаётся `docs/appcast.xml`, и адрес
  совпадает с `SUFeedURL` из `project.yml`:
  `https://mikwiseman.github.io/wai-dictation/appcast.xml`.
  Рядом лежит `docs/.nojekyll`, чтобы файлы отдавались как есть.

## Каждый релиз

### 1. Поднять версию

В `apps/macos/project.yml`:

- `MARKETING_VERSION` и `CFBundleShortVersionString` — то, что видит человек
  (`0.2.0`). Обе строки должны совпадать.
- `CURRENT_PROJECT_VERSION` — целое число, которое обязано **расти**. Именно
  его сравнивает Sparkle: версия с номером не больше опубликованного просто
  не приедет никому.

Бампу — отдельный коммит после самой работы: черновик «что нового» скрипт
собирает из заголовков коммитов.

### 2. Проверить руками то, что не проверяют тесты

```bash
./scripts/check-network-surface.sh    # сеть только там, где обещано
./scripts/test-zero-network.sh        # распознавание работает без сети
```

Второй скрипт требует уже скачанной модели и идёт несколько минут — но
именно он проверяет главное обещание продукта.

### 3. Собрать и подписать

```bash
SPARKLE_KEY_PATH=~/.wai-dictation/sparkle-key \
DEVELOPER_ID="Developer ID Application: Имя (TEAMID)" \
NOTARY_PROFILE="имя профиля notarytool" \
./scripts/release.sh
```

Что делает скрипт:

1. сверяет `MARKETING_VERSION` и `CFBundleShortVersionString` в `project.yml`
   и просит описание изменений — если файла `docs/release-notes/<версия>.md`
   нет, набрасывает черновик из коммитов и останавливается. Перепишите его
   живым языком: это увидят все, кому предложат обновиться;
2. проверяет сетевую поверхность и гоняет тесты обоих пакетов;
3. собирает, подписывает и нотаризует образ (`scripts/build-dmg.sh`);
4. убеждается, что в `Info.plist` есть `SUFeedURL` и `SUPublicEDKey`, а версия
   совпадает с той, на которую написано описание;
5. подписывает образ ключом EdDSA и тут же проверяет подпись;
6. дописывает версию в `docs/appcast.xml` — свежая первой, старые ниже, не
   больше десяти.

Первый запуск всегда останавливается на первом шаге. Это нормально: поправьте
заметки и запустите скрипт заново. Проверка стоит до сборки намеренно —
нотаризация идёт минуты, и упираться после неё в ненаписанный текст обидно.

### 4. Разложить по местам

Скрипт печатает готовые команды. По сути их три:

```bash
gh release create v0.2.0 artifacts/dmg/WaiDictation-0.2.0.dmg \
  --title "0.2.0" --notes-file docs/release-notes/0.2.0.md

git add docs/appcast.xml docs/release-notes/0.2.0.md apps/macos/project.yml
git commit -m "release: 0.2.0" && git push
```

Порядок важен: сначала образ, потом лента. Ссылка в ленте ведёт на файл
релиза, и если ленту опубликовать первой, кто-то успеет получить обновление,
которого ещё нет.

## Перед тем как расходиться

- `curl -sSf https://mikwiseman.github.io/wai-dictation/appcast.xml | head -20`
  — лента живая и содержит новую версию.
- `curl -sSfI <ссылка на образ из ленты>` — образ лежит там, куда ведёт лента.
- `spctl -a -vv -t install artifacts/dmg/WaiDictation-<версия>.dmg` —
  Gatekeeper принимает образ (нотаризация доехала).
- Поставьте **предыдущую** версию, включите в настройках «Проверять
  обновления автоматически», нажмите «Проверить обновления…» и пройдите
  установку до конца. Это единственная настоящая проверка релизного контура:
  подпись, лента и образ сходятся только все вместе.

## Про подпись: почему не `--deep`

`scripts/build-dmg.sh` подписывает вложенный код по одному, изнутри наружу:
`Installer.xpc`, `Downloader.xpc`, `Autoupdate`, `Updater.app`, потом сам
`Sparkle.framework` и только в конце приложение. Порядок и состав взяты из
документации Sparkle.

Соблазн заменить это одной строкой с `--deep` надо гасить. Apple объявила
`--deep` для подписи устаревшим, а Sparkle просит не применять его прямо:
`Downloader.xpc` подписывается со своими entitlements, которых нет у остальных
двоичных файлов, а `--deep` накрывает всё вложенное одинаковыми опциями.
Ломается при этом не сборка и не нотаризация, а установка обновления — то есть
у первого же пользователя и на той единственной дороге, по которой ему можно
было бы доставить исправление.

Честности ради: в нынешней сборке приложение не в песочнице, и список
entitlements у `Downloader.xpc` пустой — то есть терять пока нечего, и дефект
спящий. Но замечен он будет ровно тогда, когда песочница или сам Sparkle
что-нибудь туда добавят, и замечен будет уже пользователем.

Для **проверки** `--deep` наоборот нужен: `codesign --verify --deep --strict`
обходит вложенный код. Скрипт вдобавок сверяет, что каждый вложенный компонент
подписан тем же удостоверением, что и приложение, — пропущенный остался бы с
ad-hoc подписью сборки.

Отрепетировать всю последовательность без сертификата можно ad-hoc-подписью:

```bash
DEVELOPER_ID="-" ./scripts/build-dmg.sh
```

Образ получится нерабочим для раздачи, но порядок подписи, проверка и сборка
DMG пройдут те же самые.

## Идентификатор приложения менять нельзя

`is.waiwai.dictation` зафиксирован в `scripts/build-dmg.sh`, и скрипт
останавливается, если собралось что-то другое (например, конфигурация Debug —
там суффикс `.dev`). Приложению он передаётся в `codesign --identifier`
явно, чтобы не зависеть от имени продукта.

Причина простая: универсальный доступ выдаётся системой конкретному
идентификатору. Смените его — и после обновления человек обнаружит, что
горячая клавиша молчит и текст не вставляется, а причина ниоткуда не видна.

## Почему автопроверка выключена

`SUEnableAutomaticChecks: false` в `project.yml` — не мелочь и не оплошность.
Без этого ключа Sparkle на втором запуске сам показывает окно «проверять
обновления автоматически?» и по умолчанию включает проверки. Приложение,
которое обещает «сеть только по вашей команде», ходило бы в сеть само.

Поэтому:

- `SUEnableAutomaticChecks: false` — мы ответили за пользователя «нет»;
- `SUSendProfileInfo: false` — отчёт о железе и системе не отправляется;
- `SUAllowsAutomaticUpdates: false` — фоновой установки нет даже как опции.

Все три строки проверяет `scripts/check-network-surface.sh` на каждой сборке.
Если решите что-то из этого поменять — сначала поменяйте обещание в
`README.md` и в онбординге, а не наоборот.
