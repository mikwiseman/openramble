# OpenRamble 0.17.1

The app can now say where a slow dictation went.

Recognition timing had a gap in it. The time from your microphone stopping to
your text arriving was recorded, and so was the time the speech model itself
spent working — but the space between them belonged to no stage at all. Every
slow dictation this app has had lived in that space, which is why the engine
always looked healthy while the whole thing took seconds.

There is now a number for it, reported alongside the others. A dictation that
waits before the model starts says so, rather than needing the logs mined by
hand to find out.

Finishing what 0.14.0 started.

That release moved a blocking audio call off the thread pool that recognition
waits on. The reasoning was right and the fix was incomplete: writing your
recording to disk went the same way. Closing the audio file ends in `fsync` — a
call that waits for the disk and cannot be interrupted — and it was started at
the exact moment recognition began, on the same pool, so a busy disk was a slow
dictation for the same reason a slow audio device was.

Disk work now has a thread of its own, which is allowed to wait.

Both fixes and the doubled inference removed in 0.16.0 attack the same
measurement from different ends: the gap between the microphone stopping and
your text arriving.

Short recordings recognise on this Mac the way they already did on Windows,
and two settings moved to where they belong.

## Very short dictations

A recording under about a second and a quarter was handed to the speech model
as-is. The part of the model that turns sound into features needs a minimum
length and produces nothing usable below it, which is why the Windows and Linux
build has padded short clips with silence since the day it was written. This
one never did — so the same brief phrase could work there and come back empty
here.

It pads now, with the same measurement on both sides. The silence goes on the
end, so nothing you said is displaced, and the duration you see reported is
still the real one.

## The settings window

Sidebar rows could slide underneath the traffic lights when the list scrolled —
the title bar had nothing behind it, so the list showed through raw. It has a
material now, which is what lets content scroll under a title bar everywhere
else on macOS.

## Learning from edits is in Dictionary

It sat under Recognition. What it produces is dictionary entries, so it lives
with the dictionary, next to the replacements you write by hand.
