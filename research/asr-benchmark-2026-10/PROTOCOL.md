# Сначала существующие данные, затем свой eval

7 октября 2026 года. Класс сравнения: **Mac, русский и английский**, включая
переключение языка внутри фразы. Это порядок дальнейшей работы. Новые прогоны,
синтез речи и сбор записей в рамках этого обзора не выполнялись.

## 2. Ближайшая проверка — одна переменная

Первый кандидат: **transcribe.cpp 0.2.3 → 0.3.1 с тем же Parakeet Q8**.
Закрепить runtime на `3f32fbcc7bb3246851a0234263438bc3c0fa1cac`.

1. На одном Mac прогнать старый и новый runtime через существующий runner.
   Сохранить модель, настройки, подготовку аудио и текстовый pipeline.
2. Начать с короткого dev-набора и известных проблемных длинных записей.
   При изменении текста посмотреть конкретные замены, пропуски и timestamps.
3. Если кандидат исправен, повторить существующие публичные наборы и серию
   скорости. Сравнить WER по срезам, память и p50/p95; порядок запусков чередовать.
4. Решение о продукте принимать после этих результатов. Изменение памяти в
   upstream само по себе не доказывает выигрыш на нашем устройстве.

Следом — настроенные Whisper Turbo и Breeze: сначала подобрать настройки на
dev, затем опубликовать отдельные строки на том же корпусе. Для короткой
диктовки достаточно текста; обязательные word timestamps не должны искусственно
отсекать движок. Если нужен другой runtime, добавить только необходимый адаптер.
Nemotron, Qwen и другие кандидаты из [обзора](REPORT.ru.md) идут после этих шагов.

Сентябрьские контрольные результаты уже просмотрены. Повторно использовать
их для прозрачного сравнения и поиска регрессий можно; называть их новым
независимым закрытым тестом для выбранных теперь настроек нельзя.

## 3. Минимальные правила честного сравнения

- **Одинаковый вход и устройство.** Версии весов/runtime, хеши, точность,
  число потоков, язык, подсказки, VAD и обработка текста указаны у каждой строки.
  Настроенные варианты обозначаются отдельно от настроек по умолчанию.
- **Модель, runtime и приложение — разные сравнения.** Наш harness не является
  результатом официального Handy или Klava. Внешние RTX/H100-цифры не получают
  место в таблице скорости Mac. При сравнении runtime фиксируем одни веса.
- **Качество по сценариям.** Корпусный WER = сумма замен, пропусков и вставок /
  число слов эталона. Сохраняем текущую нормализацию, RU/EN/mixed и домены
  отдельно. Не усредняем проценты коротких и длинных фраз и не называем
  `100 − WER` точностью смысла. Пунктуация в текущем WER не измеряется.
- **Сбои видны.** В существующих результатах ошибка даёт пустую гипотезу и
  отдельный счётчик; не исключаем её ради улучшения оценки. Ошибка интеграции
  и отсутствие функции у модели должны быть явно различимы.
- **Скорость с ясными границами.** Прогретое распознавание готового PCM,
  обработка файла целиком и Stop→вставка — три разные величины. Для файлов
  RTFx = суммарная длительность аудио / суммарное время обработки.
  Повторы одних фраз показывают разброс задержки, а не разнообразие голосов.
- **Параллелизм учитывается полностью.** Для нескольких файлов считаем
  суммарный объём работы и память; не сравниваем пропускную способность N
  потоков с задержкой одного запроса. В streaming звук поступает в реальном
  темпе, без доступа к будущему; работа во время речи тоже расходует ресурсы.
- **Показываем неопределённость.** Сохраняем парные интервалы по группам
  исходников. Разные голоса одного TTS-текста или нарезки одной записи не
  считаем независимыми текстами. Диаграмма «качество–задержка» требует одного
  набора аудио и режима для обеих осей.

## 4. Свой eval — отдельный следующий этап

Идея ElevenLabs подходит для управляемых проверок: одни и те же числа, имена,
английские термины, отрицания и длинные фразы можно воспроизвести разными
голосами. **Сначала используем уже созданные 72 записи** и посмотрим, каких
случаев в них не хватает. Новую генерацию пока не заказываем.

Перед оценкой вручную сверяем текст с тем, что реально произнёс синтезатор.
Сценарий TTS не автоматически является верным эталоном звука. Для каждого
входа сохраняем аудио один раз и подаём всем движкам те же байты. Варианты
одного текста остаются на одной стороне dev/test.

Синтетика помогает обнаруживать регрессии, но не отвечает за естественные
оговорки, акценты, микрофоны и переключения языка. Поэтому следующий собственный
eval должен включать небольшой набор настоящих рабочих диктовок с проверенной
расшифровкой. Его размер и состав определим по пробелам первого этапа.
Масштабный сбор сотен новых записей сейчас не нужен.

Первое расширение метрик: сохранение терминов, чисел и отрицаний, пропуски
целых фраз, пунктуация и доля текстов без ручных исправлений. Не сводим их
заранее в один произвольно взвешенный «балл качества».

Итог первого этапа — таблица того, что измерено, ограничения и один следующий
проверяемый эксперимент. Итог отдельного eval — воспроизводимый набор живых
и синтетических сценариев, который помогает выбирать улучшения продукта.
